# Authorized research implementation

Use this skill only when the user has authorized a specific implementation task. Locate the repository root. Check `AGENTS.md` and the four current entry points: `SPEC.md`, `PLANS.md`, `docs/contracts/CURRENT_CONTRACTS.md`, and `docs/evaluation/CURRENT_EVAL_PROTOCOL.json`. Archived designs are historical. Read only relevant requirements, source, and tests. Existing behavior remains governed by `docs/specs/V1_SPEC.md` and `docs/contracts/V1_CONTRACTS.md` until an authorized task changes it.

This skill supplies domain methods inside the existing [project workflow](../../../docs/engineering/WORKFLOW.md). Reuse its Task ID, scope, approvals, and evidence; return results to that record without restarting the shared `engineering-workflow` or creating another sequence of gates.

1. Identify the authorized Task ID, linked requirement and acceptance IDs, affected modules, current behavior, and smallest contract change. If requested behavior conflicts with an applicable clause, identify both and obtain a design decision before changing behavior.
2. Reproduce material bugs where feasible. Plan the state, API, event, persistence, browser lifecycle, ownership, and compatibility impact actually touched. For target work, read [ADR-0005](../../../docs/design/adr/0005-windows-worker-wsl-postgres.md): Windows API/Worker and WSL PostgreSQL application tables own business truth; call attempts and fencing are durable, while any later checkpoint only assists execution recovery. P-01's two-week gate pauses paid pilot on failure. Keep `browser-use/` upstream-owned; prefer project adapter changes before an explicitly authorized upstream patch.
3. Implement within the authorized scope, with meaningful regression tests for behavior changes. Preserve unrelated work and original benchmark records. Use the applicable gates in the [workflow](../../../docs/engineering/WORKFLOW.md) and select checks by risk from the [test strategy](../../../docs/testing/STRATEGY.md).
4. Self-check the complete task-owned diff, including committed, staged, unstaged, and new-file contents, against the requirement and architecture boundaries. Run focused offline checks, then obtain independent review in a fresh context for behavior changes and the relevant specialty for high-risk boundaries. Record the reviewed base/content and exact check results. Validate findings before fixing, rerun affected checks, and independently re-review behavior changes. A real model/browser evaluation requires separate explicit cost and execution authorization.
5. Report each acceptance criterion as verified, implemented but unverified, blocked, or failed, based on actual evidence. Prepare runnable entry points, key changes, acceptance steps, skipped checks and unresolved risks for human key-business acceptance. Continue fixing test failures within approved scope and report milestones; scope/important-design changes or failed milestone business acceptance need a concrete decision. After a reviewable handoff, commit, push, and PR require task-scoped authorization naming the operations; merge and deployment remain separate.

Completion means the authorized task has a traceable scoped diff, relevant test evidence, and an honest acceptance state; implementation alone is not acceptance.
