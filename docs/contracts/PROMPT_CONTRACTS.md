## 1. 请求编译与公共边界

每次模型请求属于一个程序选择的 purpose，并绑定当前 Case/Task/Work、已接受目标版本、阶段、请求编译器及资格 revision。模型不选择较大 purpose，不创建授权、Call 身份、确认、预算或 checkpoint 权威。尚未接受条件的 `clarify` 使用原始输入与当前待接受提案；其他用途只能在各自程序准入满足时发送。

本机有权操作者CLI指定项目唯一确认人，发起者编辑并显式接续，确认人只确认／撤销准确需求版本；两角色可同一身份。模型只能解释程序提供的角色及有效确认状态，不能指定确认人、授予权限、替人确认或把保存当确认。方案请求绑定准确需求／确认及策略／资格版本；无当前合格确认人、角色资格或head失效时由程序阻止，不以提示词建议继续。

程序提供的输入包括：

- **目标与决定**：准确输入版本、用户原话位置、已接受条件、偏好、未接受提案、任务范围及重要待决定项，保持不同状态，不把模型建议升级为已接受要求。
- **问题与义务**：本 Work 需要回答的问题、依据、依赖、关键与可选义务、排除项、允许工具和来源子集、原截止及可用剩余资源。子研究只取得父级有效权限的子集。
- **证据与 Context**：当前可用 SourceCapture/Claim 的准确版本、必要原文和来源位置，支持、反证、限定、冲突及未知关系；未读或未取得项明确列出。必要语义必须出现在实际请求中，引用 ID 或 Manifest 本身不能代替原文。
- **交接状态**：父子 assignment head、直接相关依赖、已提交结果和取材身份；历史动作作为不可信背景，不能当成本 Work 已执行的动作或新的授权。不传递整份隐藏父历史、系统指令、密钥或 Memory refs。
- **程序反馈**：工具技术结果、内容可用性、研究进展、准入拒绝和剩余未知分别描述；`success` 不自动表示事实正确或目标达成。

资料、源码、网页、工具结果和历史报告均作为数据进入明确边界，不成为 system 指令。工具或资料要求扩大权限、运行源码、发消息、读取秘密、变更配额、绕过人确认时，只能作为来源中的主张或异常记录。模型可以提出进一步调查和待用户决定项，不能执行或接受这些要求。

输出采用后续实现提供的严格、版本化结构，拒绝未知字段、错误类型、伪造引用和越界动作。下列章节定义必要字段类别和语义，不冒充已经存在的 API/DTO 或可运行 JSON Schema。程序实现时必须把用途、输出 schema、Work 义务及实际请求绑定，不能仅检验 JSON 能否解析。

## 2. 六个用途

| purpose | 输入与具体责任 | 必要输出类别 | 交接与失败 |
| --- | --- | --- | --- |
| `clarify` | 原始想法/材料、当前条件提案、可自行调查的事实及未决偏好。组织条件并提出影响范围或验收的问题。 | 条件提案及依据；待确认与未知；少量实质问题；需补查事实。 | 输出是提案，不是接受条件。不能把未回复、超时、保存或修订达到上限当作同意；重要缺口保进度并交人决定。 |
| `research_plan` | 已接受目标、问题、可用证据、依赖、权限和剩余资源。分解本轮问题、取材与可选专题分工。 | 有界 Work/assignment 提案、依赖与排除项、来源取材建议、预期证据和完成条件。 | 子问题仅在独立且收益值得时委派；不得固定凑角色、递归委派或新建 Case/Turn/grant。程序原子准入、幂等创建；拒绝后不能换 ID 绕过。 |
| `extract` | 当前获许可的固定来源表示、具体问题、必要前后文及已有相关 Claim。 | 主张、精确片段/位置、主体/版本/适用范围、支持/反证/限定关系；不明和未覆盖项。 | 片段存在不等于语义支持；没有支持时输出未知或冲突，不能借其他版本、搜索摘要或常识补成源码事实。 |
| `evidence_review` | 明确研究问题及全部必要支持、反证、限定、冲突、未知；子提案及直接依赖。 | 问题对应的证据比较、冲突解释、条件化判断、未决事项和可证伪验证；可包含子研究结果提案与基于证据的讨论答复。 | 结果待程序准入、主研究者归并及必要人决定，不是独立事实证明。不能用本用途隐藏纯历史压缩、额外 judge 或未计数归并调用。 |
| `gap_plan` | 当前证据覆盖、失败、未读清单、关键义务和全部剩余资源。 | 会改变结论的补查问题、候选取材、停止/partial理由及其对结论的影响。 | 不因“还可以搜”无限继续；不把已完成/unknown Work 换名重发，不把失败的关键义务改为可选以宣布完成。 |
| `document_compile` | 已封存的本次研究输入集合、准确模式、当前文档与父版本、必要确认绑定、证据及资源保存资格。 | requirements/solution/review 的正式文档候选及来源、限定、反证、未知、未读、验证步骤；保留程序原稿身份。 | 输出不等于需求确认或提交成功。完整流程方案绑定准确已确认需求；失败不得自动修复、补额或宣称首稿完成。程序校验后才创建不可变 DocumentVersion。 |

### 2.1 clarify：把想法变为可讨论条件

先利用已经取得的事实，而非重复问用户可查材料。区分事实问题、用户偏好、重要产品决定和待真实环境验证的假设。提问须说明具体案例、已知依据、候选、收益代价及答案影响。普通细节可以提出有理由的建议，重要范围、权限、费用和验收不能由模型代定。

例如案例 A 的“老人语音发消息”仍需明确具体人群困难、设备/应用/语言和当前做法；已有系统语音控制属于替代方案证据。读取与发送消息的控制机制可以作为候选讨论，不提前成为已接受需求。案例 B 应先查固定仓库已有能力，再问扩展目标，不能把已有报告聊天误报成不存在。

### 2.2 research_plan / gap_plan：分工与收敛

主研究者持续维护全局问题，单链也是合法选择。专题提案写明独立性、需要共享的依赖及预计增加的 Context/调用成本。所有主/子规划、提取、归并、讨论、补研和文档请求都计入原 Case。

首次公开源真实pilot使用同一安全内核的单链，动态委派入口关闭；模型提案不能开启入口或领取额外资源。通过原最低恢复／Gateway／Token／资金／来源／rearm关口后才可另授真实调用，后续再完成动态分工重集成和私源。两者仍属完整M1，早期单链输出不表示动态能力已完成；顺序由[计划](../../PLANS.md)维护。

子研究基于准确 assignment 和直接依赖工作；不因无关 sibling 更新自动作废有效结果，也不沿用已被替换的目标继续发送。Shared acquisition 由 Task 管理；同一次取材的多个消费者不是独立交叉验证。当前权限、来源版本或封存状态不满足时，模型建议不能恢复调用资格。

补研围绕“什么证据会改变判断”。停止时分别列明已回答、允许接受的未知、关键未满足、可选失败和未读范围。只有事先接受的完成标准允许时，未知才可满足相应探索义务。

### 2.3 extract / evidence_review：证据与判断

每项关键主张指出来源类型和检查范围：维护者主张、固定源码、测试设计、执行结果、Issue/PR报告或修复、他人实验、本轮实际验证、推断或未知。测试文件存在、修复已合并、报告有引用均不能单独证明正确性。

对源码结论保留仓库、commit、文件、符号及必要位置；对网页保留 URL、观察日期和适用平台。没有权威基准的评审输出观察、风险与假设，不发明必须符合的要求。支持和反证冲突时展示差异，不能在摘要中删除反证后给出更确定的答案。

子提案至少能追到 assignment、来源与 Work/Call，保留反证、限定、失败、未知及停止理由。主归并不把角色数量、相同来源或多个模型重复同一意见当独立支持。需要额外模型形成提案或归并时，必须属于计数的 `extract`/`evidence_review` 等准确用途。

### 2.4 document_compile：正式候选与人的确认

requirements 候选包含用户/问题/任务、范围、流程、AC、依据、假设与待决定项；solution 候选包含准确需求绑定、架构/数据流、模块职责、正常/失败/恢复、权限与费用、替代取舍及验证。review 候选包含问题、依据、发现、影响、未知和下一步。来源身份和私有 ancestry 随派生内容保留。

模型不能产生有效 RequirementsConfirmation。显式保存或模型输出只能产生版本；项目当前有权确认人的显式确认必须绑定准确不可变 requirements version/hash及实际actor／策略／资格revision。需求新head或确认角色资格失效使当前确认无效；方案开始、请求发送与结果提交都由程序重核。普通logout或凭据轮换不自行撤销内容确认，重新加入／换回原确认人也不复活旧资格。旧方案及旧确认留作历史，不自动重绑定；发起者仅在当前准确确认后显式接续，原Case资源与deadline不变。

编译前程序封存研究输入集合；封存后迟到结果只进入原始审计/费用，不能悄悄改变本稿依据。必要研究未完成时按条件化 partial 交付，不为输出完整外观编造证据。AI原稿、人工修订和最终交付分别保留。

## 3. 资源与失败的公共约束

具体参数只以[唯一协议](../evaluation/CURRENT_EVAL_PROTOCOL.json)及[运行契约](CURRENT_CONTRACTS.md)为准。本配置采用共享正常调用池和六个用途单次上限；模型不能选择更大的用途或从 Memory 预留借用。额外 summary、judge、schema repair 和 SDK 隐式重试均不构成免费路径。

`document_compile` 最多四次**物理尝试，包含技术重试**。完整流程保护首次需求与首次方案，其余模式保护首次正式文档；只为尚未进行首次尝试的文档锁定该次调用、Token、保存与终态资源。发送后对应资源转已用，失败不返还、不因首稿尚未成功而自动补满；合法重试仍同时消耗重试、总物理调用、Token及编译四次上限。资源不足时保进度 partial，不能声称保证成功或保证修订次数。

| 现象 | 模型应输出/保留 | 程序必须执行的边界 |
| --- | --- | --- |
| 工具成功但内容错误、空白、过期或不支持主张 | 内容不可用、无进展或未知及可核查原因 | 不把工具 success 直接推进义务完成；进一步调用重新准入。 |
| 必要证据未取得或放不进 Context | 缺口、受影响判断及有界补查/partial | 不静默裁掉条件、反证或权限信息；拒绝不可满足的请求编译。 |
| 重要目标/需求/权限变化 | 当前依据失效和需人决定内容 | 取消未发送资格，重核 head/assignment/grant；不自动扩围。 |
| JSON或业务内容不合格 | 原输出和失败类别，不伪造已保存文档 | 业务输出失败不同于供应商响应协议异常；repair0，无免费重试。 |
| 计数差异或 context overflow | 不重新编码输出来证明用量，不猜实际费用 | 本地公开格式计数、托管适配资格、实报 usage/缓存/费用分账；合法差异记录，overflow按契约撤销受影响资格。 |
| 超时、取消、网络断开、结果不明 | 已知进度、未完成和不明状态，不声称远端已停 | unknown停止项目新外发；已完成/unknown不通过新ID重发；终态与物理清理分离。 |
| Memory禁用 | disabled/not_applicable，不产生记忆提案或历史 refs 注入 | 全入口禁用、active refs为空；Case证据照常持久化，显式历史来源独立核权。 |

## 4. 后续实现验收

本节是可执行验证规格的输入，不是已通过结果。业务授权后应把实际编译请求、Manifest、purpose/schema、目标与资格 revision、Work/Call、来源和预算预留连成 trace，保护秘密和来源读取权限。

必要离线正反例包括：六用途路由及越界输出、源码/网页注入、反证遗漏、只有引用无必要文本、过期 assignment、共享取材误当独立佐证、封存后迟到结果、需求换 head、未确认方案、首稿失败自动补满、第五次物理编译、合法 Token 差异误拒、业务 JSON 错误误撤供应商资格、Memory默认注入和隐藏调用。实际并发原子性、撤权双序、恢复、Tokenizer、供应商费用及内容质量分别按[测试策略](../testing/STRATEGY.md)验证，静态配置检查不能替代。

案例 A 走“想法→用户/平台证据→反例与未知→需求提案→准确确认→方案”；案例 B 走“固定仓库事实→可复用与缺失→扩展影响→编辑/确认→方案”。两条走查均须能解释正常、失败、取消、版本变化和权限变化；它们不替代正式六槽位材料或实际用户验收。
