# G0–G7 工程执行流程

本页是重复执行的步骤与关口，不另立产品、API 或评测门槛。权威顺序见根 `AGENTS.md`；每个新任务从[任务模板](TASK_TEMPLATE.md)建立唯一 Task ID，重要需求链接自己的 Spec。工作开始与结束均检查 Git 状态、证据和未完成事项。

| 关口 | 输入 → 动作 → 可核验输出 | 停线／人的决定 |
| --- | --- | --- |
| G0 审计 | 现行四入口、V1 行为、源码、状态和历史证据 → 区分现有／目标／历史 → 基线、风险、保留及迁移映射 | 缺证据标未知，不改写历史。 |
| G1 产品研究 | 用户问题与官方岗位／产品／源码 → 比较候选及成本 → 研究报告与待决问题 | 产品定位由用户决定；上游 Star 不代替实测。 |
| G2 架构研究 | 已批准产品、ADR、运行环境 → 设计并比较完整方案 → ADR 与迁移范围 | 架构、编排或新增依赖变更由用户批准。 |
| G3 需求设计 | 目标与架构 → Requirement／AC、API／状态／数据边界、异常和非目标 → 可测 Spec／契约 | 重要契约、状态、权限、费用或事实变更先审查。 |
| G4 任务计划 | Spec／AC → 依赖排序与 1–2 天纵向切片 → 任务包、估计、验收与 No-Go | 缺独立验收价值则合并，过大则拆分；付费点单列。 |
| G5 开发 | 已批准任务、干净边界和基线测试 → 最小实现与风险驱动 TDD → scoped Diff 和实际检查 | 修复范围内新增失败；基线、权限、契约、费用风险停线。 |
| G6 验收优化 | [测试策略](../testing/STRATEGY.md)、冻结协议和轨迹 → 分层检查、根因与可证伪假说 → 同口径结果 | 真实浏览器诊断和每次付费调用分别授权；失败样本保留。 |
| G7 GitHub 交付 | 达到本次代码提交条件的切片 → 暂存范围、提交说明、PR、CI、Review、回滚与交付记录 | Commit、Push、创建 PR、合并分别授权；远端门禁以实际权限和运行结果为准。 |

**Feature**：取已批准切片；读最小必要文档和调用链；保护用户工作；记录原有失败；先验证可观察行为；最小实现；按风险执行 L0–L5；高风险改动按明确路径做独立 Review；修复新增缺陷；附证据及未知事项。**Bugfix**：现象／影响 → 复现或可靠轨迹 → 调用链与根因 → 回归测试 → 最小修复 → 验证 → Review。不能复现时标证据不足。

**Agent 评测**：离线模拟、诊断 Pilot、正式批次分别标识；正式协议只由 `docs/evaluation/CURRENT_EVAL_PROTOCOL.json` 决定。每次记录版本、运行 ID、调用与事实、来源、人工核源、报告哈希、实际／未知 Token 和费用。失败按 Planner、工具、来源、Context、Memory、LLM、Worker、预算、评测核查层分类；改变一个可证伪假设后先离线回归，再请求真实复测。单次改善只作描述，不主张统计显著性。

Codex 仅读取适用规则、任务包和相关源码；三项现有 Skill 在其对应任务中按需使用。子代理仅在独立调查或风险审查有明确收益且实际权限可核实时使用；主 Agent 保持集成与最终验收责任。PR 中列出 Requirement／Task／AC、契约影响、风险、实际测试、CI、未验证项、Agent 证据和回滚路径。

**提交与放行是两个关口**：提交前按[任务模板](TASK_TEMPLATE.md)逐项列明已验证的范围、跳过的检查及原因，检查暂存 Diff、必要回归和 `git diff --cached --check`；代码可在明确标为“已实现／待验证”的状态下提交。任务范围内 AC 只有在所选风险层的证据齐备后才记完成。产品 Go 另须满足现行阶段和冻结评测协议，提交、CI 绿灯及离线测试均不改变 No-Go。
